# Unicode Safety Standard

**Established:** originally scoped to script files; **broadened 2026-07-13** per Sandra's direct instruction after a real, costly incident (see \"Why this got broadened\" below).
**Scope:** ALL fleet files, ALL filetypes. No exceptions.

---

## The rule

**Never use the em dash (`\u2014`) under any circumstances, in any filetype, anywhere in the fleet.** Not in code, not in comments, not in markdown docs, not in JSON, not in commit messages, not in chat-generated content that gets written to a file. Use a plain hyphen (`-`) or, where genuinely needed for a strong break, a double hyphen (`--`) or restructure the sentence.

This is broader than the original scoped rule (which only covered `start.ps1`/`start.bat`/`justfile`/script paths, because em dashes are a documented PowerShell 5.1 parser-crash hazard - see \"Original scoped rationale\" below). The broadened rule covers every filetype because the failure modes aren't limited to PowerShell parsing:

## Why this got broadened (2026-07-13 incident)

During a real doc-writing session, an em dash embedded in a markdown file's content caused a `str_replace`/`edit_file` tool call to fail to match on subsequent edits - not because the character itself crashed anything, but because whatever serialization path the content passed through corrupted it into a literal `\\u2014` escape-sequence string instead of a real character, silently, on write. The file looked fine until someone tried to edit it and every match attempt failed against text that visually looked identical to what was intended but wasn't. This cost real time diagnosing what looked like a tool bug before the actual cause (an em dash in the original content) was identified. Verdict: the character is not worth the recurring, unpredictable hassle across tool chains that weren't all built with it in mind. Plain hyphens have never caused this class of problem, anywhere, in any tool. Ban it universally rather than maintain a per-filetype allowlist that has to be re-verified every time a new tool touches fleet content.

## Original scoped rationale (still valid, now a subset of the broader rule)

**EM DASH is never allowed** in `.ps1`, `.psm1`, `.bat`, or `justfile` files - not in comments, not in strings. Windows PowerShell 5.1's parser can choke on the character depending on file encoding/BOM handling, causing silent script failures or `Copy-Item`-style null parameter-binding bugs. Also never use smart/curly quotes in these files for the same reason. Same applies to Tauri `backend.rs`-adjacent build scripts (see `TAURI_PRODUCTION_PITFALLS.md` #10) and any embedded JSON content strings (see `TRAPS_AND_PITFALLS.md`).

## Enforcement

`mcp-central-docs/scripts/check-unicode-safe.ps1` - run against script files. **This check should be extended to cover all filetypes, not just scripts, given the broadened scope** - flagged here as a real follow-up, not yet done as of 2026-07-13.

## Practical habit for agents (Claude, DeepSeek, or otherwise)

When composing any file content - markdown, code, config, anything - use plain hyphens for parenthetical breaks and range separators. Do not reach for `\u2014` out of stylistic habit. If a sentence structure seems to want an em dash, restructure it or use a colon, semicolon, or plain hyphen instead. This applies to content generated by an LLM and written to a file exactly as much as it applies to hand-typed content - the failure mode doesn't care where the character came from.
