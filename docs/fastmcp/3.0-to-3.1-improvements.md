# FastMCP 3.0 → 3.1 Improvements

**Last Updated:** 2026-03-17
**Status:** Active
**Applies to:** Upgrading from FastMCP 3.0.x to 3.1+
**Fleet standard:** `fastmcp>=3.1.0`

This document covers what 3.1 adds on top of 3.0. If you're coming from 2.x, read
`migration-guide.md` first — it covers the 2.x→3.0 step. Then come back here for
what 3.0→3.1 gives you.

**Good news:** 3.1 has no breaking changes from 3.0. It's purely additive.
Bumping `fastmcp>=3.1.0` in `pyproject.toml` and running `uv sync` is all most
servers need.

---

## Summary of New Features

| Feature | What it enables |
|---|---|
| `@mcp.prompt` decorator | Server-defined reusable prompt templates |
| `SkillsDirectoryProvider` | Expose skill dirs as `skill://` MCP resources |
| Platform skill providers | `ClaudeSkillsProvider`, `CursorSkillsProvider`, etc. |
| `OpenAPIProvider` | Auto-generate tools from any OpenAPI/Swagger spec |
| `ctx.sample_stream()` | Streaming LLM responses within tool calls |
| `fastmcp discover` improvements | JSON output, richer detail |
| **`CodeMode` transform** | **Agentic tool discovery + sandbox execution (3.1 headline)** |
| Google GenAI sampling handler | Third sampling handler (joins Anthropic + OpenAI) |
| Lazy-loaded heavy imports | Faster server startup |
| `search_result_serializer` | Customize CodeMode search output format |

## 1. Server-Side Prompts (`@mcp.prompt`)

### What it is

Prompts are reusable, parameterized message templates defined on the server.
Clients call `get_prompt(name, arguments)` and receive one or more messages they
can inject into the conversation context — effectively letting the server ship
instructions to any MCP-compatible client without hard-coding them there.

### Why it matters

Before 3.1, if you wanted Claude Desktop or Cursor to behave a certain way when
using your MCP server, you had to document it in a README and hope the user read it,
or put it in the `instructions=` parameter of `FastMCP()`. Prompts are a
first-class mechanism that the client can discover, list, and call.

### How to define a prompt

```python
from fastmcp import FastMCP

mcp = FastMCP("MyServer")

@mcp.prompt(
    name="expert_mode",
    description="Load expert-mode instructions for this server's tools.",
    tags={"guidance", "expert"},
)
def expert_mode(domain: str = "general") -> str:
    """Return guidance for working with this server in expert mode."""
    base = """You are working with MyServer tools. Use tool_x for X, tool_y for Y.
Always check the result's 'success' field before proceeding."""
    if domain == "sql":
        return base + "\n\nPrefer parameterized queries. Never build SQL by string concat."
    return base
```

### Return types

A prompt function can return:
- `str` — single user message
- `list[Message]` — multi-turn conversation to inject
- `PromptResult` — structured result with role annotations

```python
from fastmcp.prompts import Message

@mcp.prompt(name="system_setup")
def system_setup() -> list[Message]:
    return [
        Message(role="system", content="You are a helpful assistant."),
        Message(role="user", content="Ready. What do you need?"),
    ]
```

### Client usage

Clients that support prompts (Claude Desktop, Cursor, etc.) can list and call them:

```python
# In a FastMCP Client (for testing)
from fastmcp import Client

async with Client("path/to/server.py") as client:
    prompts = await client.list_prompts()
    result = await client.get_prompt("expert_mode", arguments={"domain": "sql"})
    # result.messages is a list of messages ready for injection
```

### Best practices

- Keep prompt names lowercase with underscores
- Add `description=` — clients show this in prompt pickers
- Use optional `tags=` for categorization in IDEs that support it
- Avoid putting frequently-changing details in prompts — they're cached by clients

## 2. Skills Provider

### What it is

The `SkillsDirectoryProvider` exposes a directory of "skill" folders as MCP resources
under the `skill://` URI scheme. Each skill is a folder with a main `SKILL.md` file
and optional supporting files.

This is the same skill format used by Claude's native skill system and by Cursor —
meaning you can bundle skills with your MCP server and have any client load them.

### Skill directory structure

```
src/my_package/skills/
└── database-expert/
    └── SKILL.md          # Main instructions (YAML frontmatter optional)
    └── examples.md       # Optional supporting file
    └── schema.sql        # Optional supporting file
```

### Registering bundled skills

```python
from pathlib import Path
from fastmcp import FastMCP
from fastmcp.server.providers.skills import SkillsDirectoryProvider

mcp = FastMCP("MyServer")

skills_dir = Path(__file__).resolve().parent / "skills"
if skills_dir.is_dir():
    mcp.add_provider(SkillsDirectoryProvider(roots=[skills_dir]))
```

Clients then see resources such as:
- `skill://database-expert/SKILL.md`
- `skill://database-expert/_manifest` (file list, sizes, hashes)

### Platform skill providers (user's installed skills)

Use these when you want to expose the skills the user already has installed:

```python
from fastmcp.server.providers.skills import (
    ClaudeSkillsProvider,    # ~/.claude/skills/
    CursorSkillsProvider,    # ~/.cursor/skills/
    WindsurfSkillsProvider,  # ~/.windsurf/skills/
)

mcp.add_provider(ClaudeSkillsProvider())
```

### When to use which

| Scenario | Use |
|---|---|
| Bundle skill with your MCP package | `SkillsDirectoryProvider(roots=[your_package/skills/])` |
| Expose user's Claude skills | `ClaudeSkillsProvider()` |
| Expose user's Cursor skills | `CursorSkillsProvider()` |
| Multiple roots | `SkillsDirectoryProvider(roots=[dir1, dir2])` |

### Skill vs Prompt

Both deliver guidance to clients, but differently:

| | Prompt | Skill |
|---|---|---|
| MCP type | Prompt (via `prompts/get`) | Resource (via `resources/read`) |
| Format | Function returning messages | Static markdown file |
| Parameterized | Yes | No (static file) |
| Client support | Prompt-aware clients | Resource-aware clients |
| Best for | Dynamic, context-dependent guidance | Rich static documentation |

You can use both on the same server — they complement each other.

## 3. OpenAPI Provider

### What it is

`OpenAPIProvider` auto-generates MCP tools from any OpenAPI 3.x or Swagger 2.0 spec.
A REST API that has 50 endpoints becomes 50 MCP tools with correct schemas, descriptions,
and parameter validation — in about 3 lines of code.

### Basic usage

```python
from fastmcp import FastMCP
from fastmcp.server.providers import OpenAPIProvider

mcp = FastMCP("MyAPI")
mcp.add_provider(
    OpenAPIProvider(
        spec="https://api.example.com/openapi.json",  # URL or file path
        base_url="https://api.example.com",
        headers={"Authorization": "Bearer my-token"},
    )
)
```

### With filtering

You don't have to expose every endpoint — filter by tags, paths, or methods:

```python
mcp.add_provider(
    OpenAPIProvider(
        spec="./openapi.json",
        base_url="https://api.example.com",
        include_tags=["users", "projects"],       # Only these tags
        exclude_paths=["/internal/", "/admin/"],  # Exclude these path prefixes
        include_methods=["GET", "POST"],           # Only these HTTP methods
    )
)
```

### Tool naming

By default, tools are named from `operationId` in the spec. If operationId is missing,
FastMCP generates names from method + path: `get_users_id`, `post_projects`, etc.

### When to use it

- Wrapping an internal REST API to make it accessible to Claude
- Quickly prototyping MCP access to any API that has an OpenAPI spec
- Building a "gateway" server that exposes multiple APIs

## 4. Streaming Sampling (`ctx.sample_stream`)

### What it is

`ctx.sample_stream()` is a streaming variant of `ctx.sample()`. Instead of waiting
for the entire LLM response, you get an async iterator of chunks as they arrive.

### Usage

```python
from fastmcp import FastMCP, Context

mcp = FastMCP("MyServer")

@mcp.tool
async def stream_analysis(data: str, ctx: Context) -> str:
    """Analyze data and stream the reasoning back."""
    chunks = []
    async for chunk in ctx.sample_stream(
        f"Analyze this step by step: {data}",
        max_tokens=2000,
    ):
        chunks.append(chunk.text)
        # You can also yield intermediate state, log progress, etc.
    
    return "".join(chunks)
```

### When to use it vs `ctx.sample()`

| | `ctx.sample()` | `ctx.sample_stream()` |
|---|---|---|
| Returns | Complete response | Async iterator of chunks |
| Use when | You need the full response before continuing | Long responses, progress reporting |
| Complexity | Simple | Slightly more code |

For most tools, `ctx.sample()` is still the right choice. Use `sample_stream` when
the LLM response is long and you want to process or report progress incrementally.

## 5. Improved `fastmcp discover`

### What changed

The `fastmcp discover` CLI now supports:

```powershell
# Human-readable output (same as before, more detail)
fastmcp discover --client claude

# JSON output for scripting
fastmcp discover --client claude --json

# Specific client
fastmcp discover --client cursor
fastmcp discover --client windsurf

# All clients
fastmcp discover
```

The JSON output is useful for fleet audits — pipe it into `jq` or PowerShell to find
servers still on old fastmcp versions.

## 6. CodeMode Transform (Experimental) — The 3.1 Headline Feature

### What it is

CodeMode is a Transform that replaces the standard tool catalog with a staged discovery and sandbox execution interface. It solves two scaling problems in one shot:

1. **Context bloat** — standard MCP loads full JSON Schema for every tool at session start
2. **Sequential round-trips** — each tool call flows through the context window individually

With CodeMode, the LLM uses meta-tools to search for relevant tools (BM25), inspect schemas for candidates, then write Python code that runs all tool calls in a sandbox. Intermediate results stay in the sandbox — they never hit the context window.

### Install

```powershell
pip install "fastmcp[code-mode]"
```

### Basic usage

```python
from fastmcp import FastMCP
from fastmcp.experimental.transforms.code_mode import CodeMode

mcp = FastMCP("Server", transforms=[CodeMode()])

@mcp.tool
def my_tool(x: int) -> int:
    """Existing tools don't change at all."""
    return x * 2
```

### Default 3-stage flow

```
1. Search("query") → candidate tool names + descriptions
2. GetSchemas(["tool_a", "tool_b"]) → full parameter schemas
3. Execute Python code in sandbox → final result
```

### Discovery tool configuration

```python
from fastmcp.experimental.transforms.code_mode import (
    CodeMode, Search, GetSchemas, GetTags, ListTools
)

# Default (3-stage)
CodeMode()

# 4-stage for complex tagged servers
CodeMode(discovery_tools=[GetTags(), Search(), GetSchemas()])

# 2-stage: search returns schemas inline
CodeMode(discovery_tools=[Search(default_detail="detailed")])

# No discovery, tiny servers
CodeMode(discovery_tools=[ListTools()])
```

### Sandbox configuration

```python
from fastmcp.experimental.transforms.code_mode import CodeMode, MontySandboxProvider

code_mode = CodeMode(
    sandbox=MontySandboxProvider(timeout=10, memory_limit_mb=256)
)
```

### Composability (key strength)

CodeMode is a standard Transform — composes with anything:

```python
# Proxy a remote server + add CodeMode
mcp.add_provider(MCPClientProvider("https://remote/sse"), transforms=[CodeMode()])

# Apply to one provider only, not the whole server
mcp.add_provider(my_large_provider, transforms=[CodeMode()])
```

### Relevance for our fleet

Our **portmanteau pattern** already solves catalog bloat differently (1 tool with `operation` param instead of 43 separate tools). CodeMode is most useful for:
- Servers with unrelated diverse tools where portmanteau doesn't fit
- Wrapping third-party servers via proxy + CodeMode
- `OpenAPIProvider`-generated tool sets (REST API with 50+ endpoints)

Full documentation: `fastmcp/code-mode.md`

from fastmcp.sampling.handlers import GoogleGenAISamplingHandler

## Upgrade Checklist (3.0 → 3.1)

For servers already on 3.0:

- [ ] Bump `fastmcp>=3.1.0` in `pyproject.toml`
- [ ] Run `uv sync`
- [ ] Test startup: `fastmcp list path/to/server.py`
- [ ] (Optional) Add `@mcp.prompt` for key usage patterns
- [ ] (Optional) Add `SkillsDirectoryProvider` if you have skill docs
- [ ] (Optional) Add `OpenAPIProvider` if wrapping a REST API

There are no required code changes — 3.1 is backward-compatible with 3.0.
