## 2026-10-21 - mujoco-mcp: trajectory binding + response invariant (opencode, human-driven session)

Follow-up to the ASPIRE probe: implemented the two conventions from its cap_harness that were actually worth stealing, because mujoco-mcp's trajectory recorder needed them anyway.

Found a real bug while reading the code: `_sim_runner.py` called `trajectory_path.write_text(...)` on every append, which truncates - so a "recording" could only ever hold the newest frame, despite the docstring promising appends and TrajectoryViewer expecting a frame list. Now opened in append mode.

Retrofit: (1) the runner writes `trajectory.meta.json` at recording start carrying schema_version, model identity (nq/nv/nu plus joint and actuator names) and `expected_start`, and appends that exact state as frame 0 so the binding is exact rather than approximating what the runner saw a few steps later; (2) `list_trajectories` now returns schema_version, an `expected_start` summary and an `integrity` block with seven checks (frames_present, meta_present, schema_supported, model_consistent, values_finite, time_monotonic, start_state_matches) - a failing recording is reported with the failing names, never silently treated as usable; (3) new `src/mujoco_mcp/responses.py` enforces the ok/error invariant (a success may not carry an error, a failure must) and `_error_response` delegates to it so there is one source of truth.

Verified by running, not just by tests: 23 new contract tests, full suite 45 passed at 42% coverage, and a live headless pendulum run recorded 537 frames with `expected_start == frame[0]` and every integrity check green (before the fix that file could only hold one frame). ruff check + format clean, pre-commit hooks passed. Commits `64a4289` (code + tests) and `988296d` (docs). Docs updated: `docs/TOOLS.md` had a header claiming 2 trajectory tools but zero sections for them, so those are now documented; `docs/CONFIGURATION.md` job-dir listing gains record.signal and trajectory.meta.json; `AGENTS.md` gotcha corrected. ## 2026-10-21 - ASPIRE probe: borrow the contract layer, no new repo yet (opencode, human-driven session)

Sandra flagged NVlabs/ASPIRE ("agentic skill discovery for robotics", Apache-2.0, v1.0 Oct 2026, arXiv 2607.00272) as possibly interesting for the robotics repos. Probed it instead of cloning it. Verdict: do NOT adopt as a dependency - needs CUDA + gated SAM3 weights + LIBERO-Pro/Robosuite/BEHAVIOR-1K, and it is paper code (5 commits), not a library. But src/cap_harness/contracts.py is genuinely good engineering and worth mining: frozen frame-explicit dataclasses, a TaskContext identity tuple (suite/task_id/language/family), trajectories bound to expected_start (drift detection at the type boundary), and an ok/error invariant where a successful result may not carry an error and a failed result must. Probed our side by inspection: mujoco-mcp has 23 tools and already covers actuation, get_state readback, export_frame, record_trajectory, run_population + population_results, train_policy, and per-job artifacts (real jobs/pop_pendulum_0..4 dirs, from an actual sweep). What it does NOT have is the exact pair ASPIRE's thesis depends on: an addressable task with a success predicate, and a persistent attempt ledger. So the loop is expressible but not evaluable. Nuance recorded: run_population varies parameters, ASPIRE varies agent-authored programs - not the same axis. Recommendation: add 3 primitives to mujoco-mcp (set_task_context, evaluate_success, attempt_log) and create a separate skillgym repo only if a second sim backend (gazebo/isaac/ros) actually needs the loop; fleet already carries 10 robotics repos, an 11th needs a real second consumer. Wrote robotics/research/2026-10-21_aspire-skill-discovery-probe.md (capability matrix, contract constraints, decision gate, reopen triggers) and indexed it plus the earlier RoboSPA assessment in robotics/README.md. Explicitly unmeasured: no iterations-to-success number exists, because the success predicate required to score it does not exist yet - do not cite one.
