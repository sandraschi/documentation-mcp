## 1. Repository Tiers (Stars)

Repositories are classified by their strategic value and maturity using a 5-tier system. This metadata MUST be stored in `glama.json` under `fleet.tier` and `fleet.stars`.

| Tier | Stars | Category | Strategic Role |
| :--- | :--- | :--- | :--- |
| **I** | ★★★★★ | **CORE** | Foundational infrastructure, security, or primary AI controllers. |
| **II** | ★★★★☆ | **PLATFORM** | High-density platform integrations (Cloud, Media, Simulation). |
| **III** | ★★★☆☆ | **AGENTIC** | Domain-specific agents or complex toolchains. |
| **IV** | ★★☆☆☆ | **UTILITY** | Single-purpose utilities or API wrappers. |
| **V** | ★☆☆☆☆ | **EXPERIMENTAL** | Proofs of concept or legacy logic. |

## 2. Industrial Health Metric (0-100%)

The "Health" of a repository is an empirical measure of its SOTA compliance. This is a computed field based on the following artifacts:

- **+20%**: **Context** — `glama.json` exists with valid `mcp` and `web` keys.
- **+20%**: **Verifiability** — `just test` recipe exists and runs via `pytest`.
- **+20%**: **Knowledge** — `llms.txt` and `llms-full.txt` exist for LLM-consumption.
- **+20%**: **Stability** — `start.ps1` and `start.bat` exist for zero-trust launch.
- **+20%**: **Industrialization** — `pyproject.toml` uses `uv` for dependency management.

## 5. External Automated Graders — Known Blind Spots (Read Before Reacting to a Bad Grade)

Third-party automated graders (Glama's TDQS, ToolBench-style scorers, etc.) evaluate **only what they can see through the MCP protocol surface**: tool names, parameter schemas, docstrings, security posture of the exposed tools. They are structurally blind to everything else a fleet repo ships — the webapp dashboard, the Tauri desktop wrapper, the in-app AI chat with bundled skills, the CUA smoke-tested install pipeline. A low grade from one of these tools is real evidence about **tool-definition quality specifically**, not a verdict on the repo as a whole.

Two practical consequences:

- **Different graders disagree because they're scoring different things, not because one is "right."** Glama's TDQS runs per-tool (B/C/A ranges observed across the fleet) and is a narrower, more specific signal than a repo-wide letter grade from a different pipeline. Don't average or reconcile scores from graders measuring different surfaces — read each for what it actually covers.
- **A grader's design opinion is not a practitioner consensus.** If a grader penalizes a design choice — the portmanteau/action-enum pattern this fleet uses deliberately, see [PORTMANTEAU_CONCEPT.md](../patterns/PORTMANTEAU_CONCEPT.md) — that's the grader's rubric, not settled community judgment. Check r/mcp or the official MCP Discord before treating a scorer's opinion as if it were a design review from actual MCP builders; they are not the same category of feedback. Automated-grade F-repo refreshes are still worth doing where the grader is catching something real (missing `llms.txt`, no `just test` recipe, etc.) — just don't let a rubric's blind spot toward webapp/desktop/AI-chat layers read as "this repo isn't good."

**Practical rule:** treat an external automated grade as one narrow, dated data point (see [ai-of-the-gaps-and-the-hype-reflex.md](https://github.com/sandraschi/vibecoding-notes/blob/main/ai-of-the-gaps-and-the-hype-reflex.md) on not overclaiming — the same discipline applies in reverse to overclaiming a *low* score means more than it does). Weight it against what the Industrial Health Metric in §2 already tracks internally, and against human venues (r/mcp, the MCP Discord, PulseMCP, Gamut) for anything resembling actual holistic quality judgment.
